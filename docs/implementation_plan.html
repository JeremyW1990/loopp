Loopp — AI Refund Support Agent · Implementation Plan

Take-home challenge: an AI customer-support agent that processes or denies e-commerce refunds, with a customer chat UI and an admin dashboard exposing full reasoning traces. Stack: TypeScript end-to-end — React (Vite) · tRPC v11 · Express · Drizzle · PostgreSQL · Anthropic Claude (raw tool calling). Live status: implementation-status.html.

§0 · Ground rules (apply to every task)

  1. Authority boundary. The LLM never authorizes refunds. Deterministic code decides eligibility; process_refund recomputes amounts from item IDs in the DB and re-runs the eligibility engine server-side. Model-supplied amounts or verdicts are never trusted.
  2. Session-scoped identity. Every agent tool resolves customerId from the conversation row, never from model input. Foreign/unknown order ids return not_found and write a guardrail trace step.
  3. Policy is single-source. Rules live as TypeScript data in packages/agent; the customer-facing markdown and the eligibility engine both derive from it. Never hand-edit the rendered doc.
  4. Money is integer cents. Everywhere. No floats.
  5. Trace everything. Every llm_call / tool_call / guardrail persists an agent_steps row with I/O JSON, attempt counter (retries are new rows), tokens, and duration.
  6. House style. tRPC v11 + superjson; zod on every external input; Drizzle for all DB access; Tailwind for UI; tests are vitest.
  7. NEVER call the real Anthropic API from tests or CI (mock the client). NEVER commit .env (public repo). NEVER weaken policy enforcement or an invariant to make something pass.

Task board

Task details

T1 · Monorepo scaffold + Postgres + schema + seed — done (pre-loop)

Merged directly to main (15fd610) before the loop was bootstrapped. pnpm workspaces (web / server / db / shared), Docker Compose Postgres 17 on :5436, full Drizzle schema including the agent_runs/agent_steps trace tables, and a 15-customer / 38-order seed whose scenarios are documented at the top of packages/db/src/seed-data.ts. tRPC proven end-to-end with superjson.

T2 · Policy engine: rules as data, rendered doc, eligibility

Single-source policy: typed rule data renders the corporate refund-policy markdown AND drives a pure, deterministic eligibility engine with exhaustive boundary tests.

Design intent. packages/agent is born here, with no LLM dependency yet. POLICY_RULES is an array of typed rule objects carrying machine parameters (windowDays: 30, thresholdCents: 50000, …) and human wording. One renderer turns it into docs/refund-policy.md (committed, sync-tested); one pure function — checkRefundEligibility(data, requestedItemIds, now) — turns the same parameters into per-item verdicts plus a refundable total and an escalation flag. Callers fetch order/items/prior-refund rows and pass plain data: the engine never touches the DB, which is what makes it trivially unit-testable and impossible for the model to bypass. Eligibility semantics: eligible iff days-since-delivery ≤ 30; escalate iff refundable cents > 50000 (exactly $500 processes); shipping is never refundable; an item already in a non-rejected refund is ineligible.

Out of scope: the agent loop and tools (T3), any DB access inside the engine, UI, server routers.

T3 · Agent core: tool loop, mock gateway, trace persistence

A raw Anthropic tool-calling loop behind runAgentTurn(conversationId, userText): session-scoped zod tools, deterministic re-validation, a mock payment gateway with idempotency keys + fault injection, and a complete trace with tokens, cost, and latency.

Design intent. The loop is ~200 lines of explicit state machine on @anthropic-ai/sdk — no framework. Tools are the security perimeter: process_refund accepts item ids + reason only (no amount parameter exists), recomputes the amount from DB prices, re-runs the T2 engine, and only then calls the gateway. The gateway demos production thinking: idempotency keys (the refund id) make retries exactly-once, and the fault_injection setting makes the first attempt per key fail so the Loom can show a real retry in the trace. Every LLM call and tool call is bracketed with timing + token capture into agent_steps; cost uses a pricing table (sonnet-4-6: $3/M input, $15/M output). A minimal chat.sendMessage mutation wires it to the API; UI comes in T4. All tests run against a scripted mock Anthropic client — the suite must be green with no API key present.

Out of scope: SSE/streaming + chat UI (T4), admin dashboard (T5), red-team harness (T6).

T4 · Customer chat UI with live agent activity (SSE)

Pick a seeded customer, converse with the agent, watch live status chips while the run executes, read the policy.

Design intent. The loop already persists steps; here it also emits them on an in-process event bus keyed by run id, exposed as a tRPC v11 SSE subscription. The chat client sends the message (mutation), subscribes to run events, and renders status chips ("checking order…", "processing refund — attempt 2…") until the final reply lands. Identity is fixed at conversation.create — the customer picker is a demo login, and no per-message customer id ever crosses the wire (that's the session-scoping rule made visible). Finished runs replay their chips from agent_steps, so reloads and late subscribers render identically.

Out of scope: admin dashboard (T5), token-by-token text streaming (status-chip granularity is the bar), real auth.

T5 · Admin dashboard: traces, escalations, chaos toggle

Observability + human-in-the-loop: full trace timeline per run, an escalation queue with exactly-once approve/reject, the fault-injection toggle, aggregate stats.

Design intent. The trace viewer is the demo centerpiece: steps in sequence with type badges, collapsible I/O JSON, red error rows, retry badges where attempt > 1, and per-step tokens/latency under a run-totals header. The escalation queue closes the loop on the >$500 rule — approve executes through the same idempotent gateway (double-click safe), reject requires a note; either way the customer's next message sees the outcome through the agent's own tools. The chaos toggle writes app_settings.fault_injection so the Loom retry moment is reproducible on demand.

Out of scope: admin auth, pagination polish, charts.

T6 · Red-team evals + README (zero-config finish)

Adversarial evidence plus the front door: a scripted attack suite proving the policy holds against the real LLM, and a README that gets a reviewer from clone to running demo in three commands.

Design intent. pnpm red-team drives ≥10 scripted multi-turn attacks through the real loop — sympathy pleading, identity spoofing, "ignore all previous instructions", fake CEO authority, the seeded injection product (ord_1018), double-refund (ord_1009), over-threshold pressure, final-sale pressure, policy gaslighting, chargeback threats — then ignores what the model said and asserts what the DB contains: zero invariant violations. The README sells the architecture: quickstart, mermaid diagram, security model, trace anatomy, red-team results table, before-prod list, and the "how LLMs built this" note the brief asks about. Finishes with a clean-clone verification in /tmp.

Out of scope: deployment/live URL, recording the video (T7).

T7 · Demo script + dry run

A timed ≤5-minute Loom beat sheet hitting every deliverable requirement, plus a pre-demo reset checklist, validated by a dry run.

Design intent. The brief's video requirements become timed beats: happy-path refund with live chips → a hold-the-line denial → chaos-toggle ON → the retry visible in the admin trace with tool I/O, tokens, cost, latency → "how I'd debug from here" → escalation approve → before-prod list. A coverage checklist maps each brief sentence to its beat so nothing is forgotten on camera.

Out of scope: recording the actual video (human), new features.
